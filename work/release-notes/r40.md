## Deyva v0.8.98-r40

Android 胶片模拟冲洗应用。光谱物理引擎移植自 [SpektraLab](https://github.com/JamesQiu2005/SpektraLab)，胶片过程模型与实测色彩数据来自 [spektrafilm](https://github.com/andreavolpato/spektrafilm)。

这一版主要是把「导入到导出」这条链上的分辨率损失和几处会崩的地方清掉。r39 之后有一批针对单机型的临时修法，这一版重新做了一遍，改成了对所有人都成立的做法。

### 导出能出到设备真正的上限（r40）

以前 RAW 解码写死长边 4096，而且交给 LibRaw 的 `half_size` 一刀切：7168 长边进来，出去是 3584 —— 比 4096 的预算还低 12.5% 线性，等于白扔 23% 的像素。用户看到「导出的不是全分辨率」，问题其实出在导入那一步。

现在分三段处理：

- **先读头**：只开文件读尺寸与机型，不 unpack，几毫秒。
- **再按设备能力算**：一张平面是 `w × h × 3 × 4` 字节且必须整块绑成一个 SSBO，所以「一次能渲多少像素」由 `maxStorageBufferRange` 决定，128 MiB 对应约 10.6 MP。这个数以前在 App 里写死，等于拿最小设备的上限给所有设备定价；现在由引擎上报真实值，256 MiB / 1 GiB 的设备直接用自己装得下的尺寸。
- **最后按任意比例缩**：面积平均，不再受 2 的幂限制，7168 → 4096 是精确缩放而不是砍半。

另外把解码结果**直接开成引擎会话**，不再先变成一份 Java `float[]`。45 MP 的 float RGB 是 440 MB，光这一份拷贝就足以让堆先炸 —— 以前「不敢解全尺寸」有一半是这个原因。现在像素全程留在 native 堆，上传完立刻释放。

所以：**设备装得下就是相机原生像素**；装不下时会按本机最大可行尺寸出图，并在导出面板与结果里写明「相机原生 X → 工作源 Y，少百分之几」，不再让用户猜。这条硬上限来自 GPU 单块缓冲，不是可以靠调参绕过的。

### 大图导出不会再缺一块（r40.2 – r40.6）

20 MP 以上的 RAW 导出，有时会看到整张图缺一条、或者下半截、上半截直接是黑的。查到根因是 GPU 在大缓冲上做整块拷贝和写回时**命令返回成功、但有一部分行并没有真正被写入**：20 MP 时一块平面是 295 MB，出错的位置每次都不一样（实测四次分别缺在下方 40%、中部、底部 15%、顶部 32%），所以不是某个固定的越界或算错。

这一段的做法是**不再假设「没报错就等于写对了」**，改成每一步都验、每一帧都要全：

- **拷贝分块**：所有 GPU 侧的拷贝与回读按 2 MiB 切块、逐块提交并等待。单块出问题不再拖垮整次传输，失败时日志会指明是哪一块。
- **回读校验**：负片缓存拷完后，首行 / 中间行 / 末行逐字节比对，不一致就重拷一次；仍不一致明确标失败，而不是带着坏数据继续冲印。
- **导出前归还显存**：把渲染池里已经没人使用的缓冲还回去（实测一次腾出近百 MB）。大图导出失败往往就是池子被上一轮占满。
- **渲染自愈**：一帧出来后先扫全零行（16 bit 下真实暗部不可能整行三个通道恒为 0）。缺了就同尺寸重渲，最多三遍逐行合并；仍只剩不到 1% 的缺口时用最近的非空行填平；缺口更大则自动降一档长边重渲，直到交出一张完整的图。

原则很简单：**宁可多花十几秒重渲，也不交出一张缺角的图。** 每一步都写在诊断日志里（`渲染自愈` / `EXPORTCHECK`），能看出这张图是靠哪一步救回来的。

### 导出不会再把 GPU 打挂（r40）

`full` 档恒等于源图尺寸，引擎不会自己降档。开片边时画布放大 1.528 倍，2448×3248 就要 139 MiB，必然超；不开片边，4096 长边 3:2 也正好贴死 128 MiB 红线。

现在导出**渲染之前**就按预算判定：超了就用 `live` 档配一个临时的工作长边（画布面积 ∝ 长边²，反解出刚好落进预算的值），渲完无条件把预览尺寸还回去。真的撞上 `VK_ERROR_DEVICE_LOST` 时，会识别出来并重建引擎恢复预览 —— 设备丢失后同一个 VkDevice 上再降档也没用，以前的表现是「导出失败，之后连预览都不出图」。

用户选的导出台阶（2048 / 1600 / 1280）现在直接按那个尺寸渲染，不再「先渲全幅再缩」白算一遍。

### 右下角那条黑边没了（r40）

LibRaw 0.22.2 只对机型表里的机身下有效成像区裁剪规则。没收录的新机走兜底 `width = raw_width`，整块传感器帧连同右侧/下方的光学黑遮罩行列一起 demosaic，扣完黑电平约等于 0，冲印出来就是纸黑偏蓝的一条边。

修法不写死机型：解码后、降采样前逐列/逐行检测，四道护栏 —— 列/行均值、后缀遮罩密度 ≥90%、右与下必须同时命中、遮罩带比紧邻画面暗 4 倍以上。整幅极暗的夜景不会被误裁；单边黑条也不动手。

### 相册里看不到的 RAW 也能导（r40）

顶栏「导入照片」旁边多了一个「导入文件」，走系统文件选择器直接读原始文件。不少 ROM 的相册会把 RAW 过滤掉，或者只给一张转码后的预览 —— 用户的原话是「A7 拍的 ARW 根本不在列表里」。扩展名会先挡一道，选到非图片文件会提示而不是默默失败。

### 一张解不开的图，不再把整个 App 变成白板（r40）

旧版在解码**之前**就清空缩略图缓存：一旦解码失败，胶片条直接变一片白。现在清空挪到解码成功之后，失败时保留上一张，诊断日志里也会写明具体原因（LibRaw 的哪一步失败、机型与解码器是什么），而不是只有一个 `Log.e`。

### 尺寸显示不再显示成「1 × 0」（r40）

导出面板的「尺寸」存的是档位**索引**（0/1/2/3），旧代码把它当像素用：选「2048」（索引 1）时面板显示 `1 × 0 · 0.0 MP`；竖幅照片还会把源图宽度当长边算。现在按档位的真实像素值等比换算长边，横向纵向都对，并且与导出时实际使用的缩放算法共用同一套。

### 索尼 ARW 6.0：A7 V 的 Compressed / Compressed HQ（r40）

ARW 6.0 有三档：未压缩、Lossless（`sony_arw2_load_raw`）、Compressed / Compressed HQ（`tiff_compress = 32766`）。LibRaw 0.22.2 没有 32766 分支，会落到 `default: is_raw = 0`，`unpack()` 直接失败 —— 表现就是导入报错、预览空白。

这一版把上游 LibRaw 0.23 的 `sony_arw6` 解码器（PR #824）移植进来，五处挂钩：`tiff.cpp` 的 32766 分支、内部函数声明、`identify` 的 ILCE-7M5 有效尺寸、色彩矩阵、解码器名。全部改动包在 `SPEKTRA_ARW6_DECODER` 宏内，关闭时与官方 0.22.2 逐位一致。

诊断日志里会写 `RAW 头：Sony ILCE-7M5|7028x4688|sony_arw6_load_raw()|arw6=1`，真机一眼能确认这一档走的是哪个解码器。

### 已知边界

- 相机原生全分辨率仍受 GPU 单块缓冲上限约束：单块 128 MiB 的设备约 4000 长边（3:2），256 MiB 约 5600。要突破得把渲染画布改成分块 SSBO，那是引擎级改造，不在一版之内。设备实际可用的上限由引擎上报、导出前按实测死线判定，不再写死。
- ARW6 解码器来自 LibRaw 未发布的分支，目前没有真实的 A7 V 压缩 RAW 样本做过逐像素比对；验收凭据是日志里出现 `sony_arw6_load_raw()` 且能出图。
- 大图导出如果走到「降一档长边」，会在日志里写明最终尺寸；这是自愈的兜底路径，不是正常路径。
